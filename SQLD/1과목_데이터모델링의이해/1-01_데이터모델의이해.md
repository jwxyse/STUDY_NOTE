## 1. 모델링의 개념

- 현실 세계의 업무 흐름과 데이터 요구사항을 **추상화·구조화**해서 표현하는 과정
- 데이터의 **구조, 속성, 제약, 관계**를 정의해서 저장·활용 기준을 마련

> ⭐ ✏️ 데이터 모델링 = **어떤 테이블로 만들고 어떻게 관리할지 설계하는 과정**
> ⭐ 흐름: 현실 업무 → **Abstraction(추상화)** → 데이터 → **Structured Representation(구조화된 표현)** → 모델

---

## 2. 모델링의 특징 ⭐

| 특징 | 설명 |
|---|---|
| **단순화** (Simplification) | 불필요한 세부사항은 빼고 **핵심만** 남겨 정리 → 이해·설명이 쉬워짐 |
| **추상화** (Abstraction) | 일정한 규칙·표기법으로 **간략하고 대략적으로** 표현 → 누가 봐도 같은 의미로 이해 |
| **명확화** (Clarity) | 애매함을 줄이고 **정확하게** 표현 → 오해 없는 의사소통 |

> ✏️ 추상화 ↔ **구체화** (반대 개념)
>
> ⭐ **구조화 ≠ 구체화**
> - **구조화**: 여러 데이터를 규칙과 관계에 맞게 정리하는 것
> - **구체화**: 추상적으로 생각한 내용을 실제로 표현·구현할 수 있게 상세하게 만드는 것

---

## 3. 데이터 모델링 3가지 요소 ⭐⭐

| 요소 | 설명 |
|---|---|
| **대상** (Entity) | 업무에서 관리해야 하는 사물, 사람, 개념 등의 객체 |
| **속성** (Attribute) | 대상이 가지는 특징이나 정보 |
| **관계** (Relationship) | 대상들 간의 연결·연관성 |

> ✏️ 3가지 요소 = **산출물(ERD)에 들어가야 하는 요소**
> ✏️ 속성 = **컬럼, 열**
> ✏️ 예) 카페
> - 엔터티 → 고객, 상품, 재고 등의 데이터
> - 속성 → 고객의 고객번호, 전화번호, 이름 등

### ERD 예시 ⭐

```
 [CUSTOMER]          [PURCHASE]              [ITEM]
 CUSTOMER_ID  ───<   PURCHASE_ID     ──┼─<   PURCHASE_ID(FK)
 NAME                CUSTOMER_ID(FK)         LINE_NO
                     PURCHASE_DATE           PRODUCT_ID
                                             QTY
                                             UNIT_PRICE
```
- 박스 이름(CUSTOMER, PURCHASE, ITEM) = **① 대상(엔터티)**
- 박스 안의 항목 = **② 속성**
- 박스를 잇는 선 = **③ 관계**

---

## 4. 데이터 모델링 3가지 관점

> ✏️ 이해 위주로 보기

| 관점 | 설명 |
|---|---|
| **데이터** 관점 | 데이터가 어떻게 **저장·구조화·관리**되는지 정의 |
| **프로세스** 관점 | 시스템이 **무슨 일**을 하고 작업이 어떻게 조직되는지 정의 — 데이터가 시스템 안에서 **어떻게 흐르고 처리**되는지 |
| **데이터와 프로세스** 관점 | 두 관점을 **통합**해 시스템 전체를 이해 — 각 프로세스가 어떤 데이터를 **사용·생성·변경**하는지 정의 |

---

## 5. 데이터 모델링 유의점 ⭐⭐

> ✏️ 데이터 모델링에서 **하면 안 되는 것**

### 5-1. 중복 (Duplication)
- 같은 정보는 **한 곳에서만 관리**하도록 설계
- 여러 테이블에 같은 데이터를 저장하면 관리 비용 증가, 오류 발생

> ✏️ 데이터가 변경될 때 **데이터 불일치** 발생
>
> ⭐ **외래키 중복 vs 중복**
> - 관계에 필요한 키값 반복 = **정상적인 관계 표현**
> - 같은 의미의 속성값을 여러 곳에 불필요하게 저장 = **중복**

### 5-2. 비유연성 (Inflexibility)
- 작은 업무 변화에도 테이블 구조를 계속 고쳐야 하는 상황을 피해야 함
- **데이터 구조는 업무 절차(프로세스)와 최대한 분리**해서 설계

### 5-3. 비일관성 (Inconsistency)
- 데이터 간에 **모순되거나 다른 결과**가 나오는 상태
- 데이터 간 연관성과 규칙을 명확히 정의해야 함 → **데이터 품질 관리의 핵심**
- 중복이 없어도 업데이트 오류, 규칙 미정의 등으로 발생 가능

> ✏️ 예) 숫자 단위도 일치하게 저장

---

## 6. 데이터 모델링의 3단계 ⭐⭐⭐

> ⭐ **데이터 모델링 순서: 개념 → 논리 → 물리**
> ⭐ 갈수록 **추상화가 낮아짐** (구체적이 됨)

### 6-1. 개념적 모델링
- 업무 중심, 전사적 관점의 **고수준** 모델링
- 업무 분석으로 **핵심 엔터티를 식별**하는 단계
- **추상화 수준이 가장 높음**
- 엔터티 간 관계를 표현하기 위해 **ERD 초안** 작성

### 6-2. 논리적 모델링
- 개념적 모델을 바탕으로 **세부 속성, 식별자, 관계를 구체적으로 정의**
- 구조가 명확해지므로 비슷한 업무·프로젝트에서 **논리 모델 재사용** 가능 → 쿼리도 같은 구조로 작성되어 **재사용·표준화**
- 이 단계에서 **정규화 수행** → 데이터 중복 감소, 품질 향상
- 재사용성이 높아 유지보수 부담이 줄어듦

> ✏️ 논리적 모델링 → **ERD 완료 단계**
> ✏️ 세부 속성 예) 고객 이름, 전화번호 등 / 식별자 = 각 행을 식별하는 것
> ✏️ **정규화** = 하나의 큰 테이블을 적절하게 분리해서 중복과 이상현상을 줄이는 작업
> → 중복 데이터 제거 → 데이터 일관성 유지 → **삽입·수정·삭제 이상현상 방지**
>
> ✏️ 쿼리 = SQL로 작성한 요청문 (SQL = 언어)
> 쿼리: 데이터베이스에 원하는 작업을 요청하는 명령문

### 6-3. 물리적 모델링
- 논리 모델을 **실제 데이터베이스 구조로 구현**하는 단계
- 성능, 저장 구조, 보안, 가용성 등 물리적 요소 고려
- **가장 구체적**, **추상화 수준이 가장 낮음**

> ✏️ 현업에서는 개념·논리는 **데이터 모델러**가, 설계를 넘겨받아 물리는 **DBA**가 담당

## 7. 스키마와 3단계 구조 ⭐

### 7-1. 개념
- 모델링으로 설계한 **데이터 구조**는 실제 DB에서 **스키마**로 표현됨
- 스키마 = 데이터의 **구조와 제약조건을 논리적으로 정의한 메타데이터**
- 사용자·논리·물리 관점으로 나누어 관리하기 위해 **외부·개념·내부 스키마** 3단계 구조 사용

> ✏️ 메타데이터 = 데이터 설명
> ✏️ 스키마 = 데이터베이스의 설계도. 데이터가 어떤 구조로 저장될지 정의하는 것 = 데이터가 들어갈 구조와 규칙
> ⭐ 스키마 = **데이터베이스 구조와 제약조건을 정의**

### 7-2. 스키마의 3단계

> ✏️ 관리 목적으로 나눔

| 구분 | 설명 |
|---|---|
| **외부 스키마** (사용자 관점) | 개별 사용자·응용 프로그램 관점의 스키마. 필요한 데이터만 정의 (대표 예: **View**) |
| **개념 스키마** (논리 관점) | 여러 외부 스키마를 통합한 **DB 전체의 논리적 구조**. 개체, 속성, 관계, 데이터 타입, 제약조건 정의 |
| **내부 스키마** (물리 관점) | 데이터가 **물리적으로 어떻게 저장**되는지 정의. 저장 구조, 파일 구조, 인덱스 등 |

> ✏️ 외부 스키마 = 사용자가 바라보는 관점
> ✏️ 내부 스키마 = 디스크 등 어디에 저장했는지

### 7-3. 스키마의 독립성
- 물리적·논리적 구조를 바꿔도 **응용 프로그램에 영향을 주지 않아야** 함

| 구분 | 설명 |
|---|---|
| **논리적 독립성** | **개념 스키마**가 바뀌어도 외부 스키마·응용 프로그램에 영향 없음 |
| **물리적 독립성** | **내부 스키마**가 바뀌어도 개념·외부 스키마에 영향 없음 |

> ✏️ 논리적 독립성 = "**외부 // 개념**" 독립
> ✏️ 물리적 독립성 = "**개념 // 내부**" 독립

## 8. 데이터 모델의 표기법 (ERD)

- **ERD**(Entity Relationship Diagram): 엔터티와 엔터티 간 관계를 **시각적으로 표현한 다이어그램**
- 1976년 **피터 첸(Peter Chen)** 이 제안, 데이터 모델링의 표준 방식
- 실무에서는 ⭐ **IE 표기법, Barker 표기법**을 주로 사용

> ✏️ 표기법 = 어떻게 표현하는지

### ERD 작성 절차 (6단계)
1. **엔터티 도출** — 업무 분석으로 엔터티 후보 식별·목록화
2. **엔터티 배치** — 관계 파악이 쉽도록 배치
3. **엔터티 간 관계 설정** — 연관성을 찾아 관계선으로 연결
4. **관계명 서술** — 관계의 의미를 명확히 표현
5. **관계의 참여도 기술 (카디널리티)** — 1:1, 1:N, N:M
6. **관계의 필수 여부 확인 (옵셔널/맨더토리)** — 관계가 반드시 있어야 하는지 결정

> ⭐ ✏️ ①~③ = **ERD 요소**
> ✏️ ① 엔터티는 **왼쪽 → 오른쪽, 위 → 아래** 방향으로 도출
> ⭐ → **좌측 상단 엔터티가 제일 핵심**
> ✏️ ④ 관계명 설정은 **생략 가능**

## 🤔 헷갈린 점 (틀린 문제)

### Q1. 데이터 모델링 관점 중 다음 설명에 해당하는 것은?
- 데이터가 **처리되는 과정**에 초점, 데이터가 **어떻게 변형되고 이동**하는지 정의
- 시스템이 **어떻게 데이터를 처리**하고 변환하는지 과정과 동작을 정의

① 데이터 관점 ② 프로그램 관점 ③ 프로세스 관점 ④ 데이터와 프로세스 관점

- ❌ 내 답: ④ 데이터와 프로세스 관점
- ✅ 정답: **③ 프로세스 관점**
- 💡 "처리되는 과정", "어떻게 처리", "어떻게 흐르는지" → **프로세스 관점**
  - 데이터와 프로세스 관점은 **어떤 데이터가 생성되고 어떤 데이터가 제거되는지**(사용·생성·변경)를 세부적으로 정하는 것

## ⭐ 시험 포인트 정리

1. 데이터 모델링 = 어떤 테이블로 만들고 어떻게 관리할지 **설계**하는 과정 (추상화 → 구조화된 표현)
2. **모델링의 특징**: 단순화, 추상화, 명확화 (구체화 ✕) / **구조화 ≠ 구체화**
3. **3가지 요소**: 대상(엔터티), 속성, 관계 → ERD에 들어가는 요소
4. **유의점**: 중복, 비유연성, 비일관성 / 외래키 반복은 중복이 아니라 정상적인 관계 표현
5. **3단계 순서**: 개념 → 논리 → 물리 (추상화 수준 높음 → 낮음)
   - 개념: 핵심 엔터티 식별, ERD 초안, 추상화 최고
   - 논리: 속성·식별자·관계 정의, **정규화 수행**, ERD 완료, 재사용·표준화
   - 물리: 실제 DB 구현, 가장 구체적
6. **스키마** = DB 구조와 제약조건을 정의 / 외부(사용자, View)·개념(논리, 전체)·내부(물리, 저장)
7. **독립성**: 논리적 = 외부//개념, 물리적 = 개념//내부
8. 실무 ERD 표기법: **IE, Barker** / ERD 요소: 엔터티 도출·배치·관계 설정 / 좌측 상단 엔터티가 핵심
